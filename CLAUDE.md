# FamilyPhotos Server - Development Guide

A self-hosted photo and video server for families, written in Rust. It serves a server-rendered web UI
(Askama + HTMX + vanilla ES modules) and the `/api` used by the Android app.

This guide describes the `webui` branch (`main` + the web UI rewrite). Planning notes are local and untracked in
`docs/web-ui-plan/` (`01-architecture.md` = the shared contracts, `02-product-spec.md`, `progress.md`): never
commit them or reference them (or work-package names) in code, comments or commit messages.

## Quick start

```bash
cargo build --release && cargo run      # needs SERVER_PORT and STORAGE_PATH (see below)
npm install                             # once: Tailwind, Playwright (Chromium), TypeScript, knip
npm run dev                             # rebuilds assets/css/main.css on change
scripts/check.sh --port <p> [--firefox] # every check that runs before a merge (see Testing)
```

## CLI

```bash
familyphotos users create -u <user_id> -n <display_name> -p <password>
familyphotos users remove -u <user_id>
familyphotos users list
familyphotos photos scan-photos        # filesystem scan (writes to the DB)
familyphotos photos generate-previews  # generate missing previews (reads the DB only)
```

The CLI opens its own DB pools, so while the server runs it is a second writer process: a long
`scan-photos` can make the server's writes wait (up to `busy_timeout`, 60 s) or fail.

## Backend patterns

### Handlers
```rust
async fn handler(
    State(state): State<AppStateRef>,
    AuthenticatedUser(user): AuthenticatedUser,   // 401 if not logged in
) -> HttpResult<impl IntoResponse> {
    let photo = state.read_pool.get_photo(id, &user.id).await?.ok_or(HttpError::NotFound)?;
    …
}
```
Pages take `ctx: PageContext` instead (it includes the user and prefs) and render an Askama template;
grids and the viewer call `ctx.viewer_context(&context)`. Fragment routes live under `/ui/*` and return
401 + `HX-Redirect: /login?next=…` when logged out.

### Pools — one writer
- `read_pool`: several read-only connections. Use it for every read, including inside handlers that
  write later (re-check inside the write transaction when it matters).
- `write_pool`: **exactly one connection; all writes.** Never hold it during slow work (file IO, network,
  hashing, image processing): do that first, then open a short transaction. Use a transaction when
  several statements must be atomic (`state.write_pool.begin().await?`).
  Exceptions on purpose: move and trash cleanup keep the connection while moving/deleting files, so
  the DB and the filesystem stay consistent.
- Sessions go through `db::SessionStore`: `load` on the read pool, `create/save/delete` on the write
  pool. `UsersRepository` reads on the read pool, writes on the write pool.
- The file scan (`tasks/file_scan.rs`) reads rows on the read pool, walks the disk in `spawn_blocking`,
  and only if something differs takes one short write transaction per user that re-checks each change.
- Background hashing/thumbhashing works in batches (keyset by id): read on the read pool, compute with no
  connection held, one short write per batch.

### Errors
`HttpResult<T>` and `HttpError` variants (`NotFound`, `Unauthorized`, `BadRequest(msg)`, …). A 400's
text is shown to the user by the web UI; 500 bodies are not.

### `/api` is a contract
The Android app depends on every `/api` route, status code and JSON shape. **No non-additive change to
an existing `/api` endpoint without the owner's explicit OK**; report any behaviour change. Partial
success is part of the contract: `POST /api/move` returns 200 with only the photos it moved.

## Ownership and permissions

- **Public** photos/folders have `owner_id IS NULL`: any authenticated user can fully manage them.
- **Private** ones belong to `owner_id`; others reach them only through folder permissions (sharing):
  `grantee_id` (a user, or NULL for everyone), `can_upload`, `can_delete`, `expires_at` (NULL = never),
  `token` (link sharing).
- `PhotoAccess` levels for queries: `Own` (own + public), `Read` (+ shared folders with a non-expired
  permission), `Delete` (+ shared folders with `can_delete`).
- Uploads to a shared folder need `can_upload`; trash/delete in a shared folder needs `can_delete`.
- **"Delete forever" (`/api/delete/{id}`) is owner-only** (own or public photos); a `can_delete` grantee
  can trash and restore but not delete permanently.

## Event logging (sync)

- `photos_event_log`: every photo INSERT/UPDATE/DELETE logs a row (`data` = Photo JSON, NULL = deleted).
  Clients poll by `event_id`.
- `folder_event_log`: per-folder membership. A photo entering a folder (insert, move in, restore) logs
  `data` = Photo JSON; leaving it (move out, trash, delete) logs NULL. A trashed photo is never logged as
  present. The last 500 events per folder are kept; an older cursor is stale and gets the full list.
- `update_photo` in the repo does all of this by comparing the old and new state: use it for updates.

## Web UI architecture (see `docs/web-ui-plan/01-architecture.md`)

- **Pages:** `/` (timeline, `?filter=all|personal|family|shared`), `/folders`, `/folders/{id}`,
  `/favorites`, `/utilities`, `/trash`, `/duplicates`, `/large-files`, `/settings`, `/upload`, `/login`.
  Any page + `?photo={id}` opens the viewer (deep link).
- **Contexts (`contextKey`):** every grid and the viewer work on a server-defined ordered list:
  `timeline:<filter>`, `folder:{id}`, `favorites`, `trash`, `large-files`, `memories:{years}`
  (`PhotoListContext`, queries in `repo/context_repo.rs`).
- **Grid protocol:** the page renders every month section up front with its count (stable scroll
  height); JS loads `/ui/grid/month?ctx=…&month=YYYY-MM&offset=…` (≤ 200 tiles) near the viewport and
  unloads far sections. The month summary and month page queries must use the same predicate and month
  expression (tested invariant).
- **Photo tile:** one macro (`templates/macros/photo.html`) from `PhotoTileView`.
- **JS:** components mount via `data-component="name"` (`core/registry.js`, also after HTMX swaps).
  No inline handlers, no globals except `window.htmx`. Cross-module communication uses `fp:*`
  CustomEvents (`core/events.js`: `fp:photo-activate`, `fp:photos-removed`, `fp:photos-added`,
  `fp:photos-changed`, `fp:selection-change`, …). `core/api.js` redirects to login on 401.
- **Prefs:** one cookie `fp_prefs` (filter, zoom, folder sort/view), read server-side by `Prefs` so the
  first paint is right.
- **Assets:** `ASSET_VERSION` (from `build.rs`) is appended as `?v=`; versioned CSS/icons/vendor files
  are immutable in release, `/assets/js/**` is `no-cache` (ES module imports can't carry `?v=`).
- **Service worker:** `assets/sw.js`, served as `/sw.js` (`http/service_worker.rs` fills in `ASSET_VERSION` and the
  files to precache, so a new asset version is a new worker). Release: the shell is precached per version and
  served from that cache; a new worker waits and the "Update available" toast lets it take over. Previews
  (`/api/preview/*`) are cache-first (cap 5 000, oldest first) and the cache is emptied on sign-out and on opening
  `/login`; navigations fall back to `assets/offline.html`. Nothing else is cached. A dev server (`ASSET_VERSION=dev`)
  caches only the offline page. Add a new asset directory to `PRECACHED_DIRS`.
- **CSP:** strict everywhere (no inline scripts, no eval). Only `/upload` and its hash worker also allow
  `'wasm-unsafe-eval'` (BLAKE3 in WASM).
- Styling: Tailwind CSS 4 + DaisyUI 5. Feature CSS goes in `templates/css/` and is imported by
  `templates/input.css`. Icons: add the name to `scripts/icons.txt`, run `npm run icons`.

## Database and SQL

- SQLite, WAL mode. Migrations in `migrations/` run on startup.
  **No new migration without the owner's explicit permission.** Reversible `.up`/`.down` pairs are
  allowed (the e2e harness skips `*.down.sql`); `sqlx migrate add` infers the kind from existing files, so
  pass `--simple` or `-r` explicitly.
- SQL in Rust code is written in **lowercase**.
- Dates (`created_at`, `trashed_on`, `expires_at`) are stored as UTC text (`photos.created_at` as
  `YYYY-MM-DDTHH:MM:SS[.f]Z`; `photos_repo` normalizes it on every write). Compare with `datetime(...)` on
  both sides. Month grids group with `substr(created_at,1,7)` and filter with a `>= 'YYYY-MM' and <
  next month` range so `idx_photos_folder_created` / `idx_photos_user_created_at_desc` are used.
- **sqlx 0.9 + SQLite nullability:** sqlx guesses nullability from the query plan, and the guess for
  `returning` columns and computed expressions is unreliable (it depends on the DB used to prepare).
  Annotate them explicitly: `col as "col?"` for nullable, `col as "col!"` for non-null.
- **`.sqlx` cache:** only production queries. Run `cargo sqlx prepare` **without** `--all-targets`
  (no `.sqlx` files for test-only queries), against a freshly migrated empty database. Some files'
  `type_info` flips with DB statistics; that's harmless, don't commit that churn.
- Run cargo with a real `DATABASE_URL` (`sqlite:<path>`, created with `sqlx database create && sqlx
  migrate run`); `SQLX_OFFLINE=true` only works for non-test builds. `.env` points at the owner's dev
  data (`test.db`): never run tests or migrations against it.
- `axum-login` and `tower-sessions-sqlx-store` are pinned to upstream git revisions until a release
  using sqlx 0.9 is published (issue #83).

## Environment variables

| Variable | Required | Description |
|---|---|---|
| `SERVER_PORT` | Yes | Port to listen on |
| `STORAGE_PATH` | Yes | Root path for photo storage |
| `DATABASE_URL` | No | SQLite database **file path** (default `${STORAGE_PATH}/.familyphotos.db`) |
| `PREVIEWS_PATH` | No | Preview storage (default `${STORAGE_PATH}/.previews`) |
| `SCAN_NEW_FILES` | No | Background file scanning (default true) |
| `BACKGROUND_THREADS_COUNT` | No | Rayon thread pool size (default: auto) |
| `ALLOWED_ORIGINS` | No | Comma-separated CORS origins |

Login (`POST /api/login`) takes a form-encoded body (`user_id`, `password`). The session cookie is
`Secure`, so plain-HTTP deployments other than localhost won't keep a session.

## Testing

- `scripts/check.sh --port <p> [--firefox]` runs, in order: cargo build, test, clippy
  (`-D warnings`), fmt, `sqlx prepare --check`, `npm run prod`, `npm run typecheck`, `npm run knip`,
  JS unit tests and the e2e suite. It never uses `.env`: it creates `<target>/fp-check.sqlite`.
  `--firefox` adds the Firefox project; 3 Firefox failures are known (`grid.spec.ts:428` flaky,
  `viewer.spec.ts:432` clipboard permission, `viewer.spec.ts:475` H.264 in Playwright's Firefox).
- Rust repo tests live next to the repo (`#[cfg(test)]`) and use `repo/tests.rs`: `USERS` (alice, bob, carol) +
  `insert_users(pool)`, `photo(owner, name)` (customise with `Photo { .., ..photo(..) }`) + `insert_photo`,
  `create_test_folder`. `Dataset::create(pool)` (after `insert_users`) covers every access case from alice's view
  (own, public, shared view-only, shared can-delete, expired share, unshared, others', trashed); its doc comment
  lists the names: assert on `data.id("shared_1")` / `data.names(ids)`, extend it for new access cases.
  Dataset photos have no extension (don't use them for media-label assertions).
- Handler tests: `src/http/api/tests/` (and `pages/*_tests.rs` for `/ui/*`). `TestServer::new(pool)` = the real
  router with sessions, temp storage and `USERS`; `server.login("alice") -> Client`, `server.anonymous()`,
  `server.write_file(..)`, `server.state`. `Client::{get, post, put, patch, delete, request, upload}` →
  `TestResponse` (`assert_status`, `json`, `text`, `header`). Closures that call a client must be `async |..|`.
  Unit tests are `(input, expected)` tables with the input in the assertion message.
- E2E (Playwright, `playwright/specs/`): the harness starts a fresh seeded server per run on
  `FP_E2E_PORT` (default 8081). Users: alice, bob, carol (owns no photos), dave (password-change test
  only), plus the per-spec users below. Selectors are `data-testid`; no `waitForTimeout`, no
  `if (visible)` guards. Needs Node ≥ 22.13.
- Specs that mutate state have their own users: erin (trash), frank (`android-api`), grace/hank
  (utilities), heidi (selection), ivan (upload), judy (viewer); carol is read-mostly (seeded duplicates,
  sharing grantee, `security.spec.ts`). Use `PLAYWRIGHT_BROWSERS_PATH=0` when running playwright by hand.
- Playwright blocks service workers (they hide requests from `page.route`); only `service-worker.spec.ts` allows them,
  and contexts you create by hand need `serviceWorkers: 'block'`.
- `a11y.spec.ts` (axe: zero serious/critical), `security.spec.ts` (carol can't reach alice's private
  photos), `android-api.spec.ts` (the `/api` contract end to end). `FP_E2E_WEBKIT=1` adds WebKit and
  Mobile Safari (needs the system libraries of `npx playwright install-deps`).
- Large-data checks: `scripts/seed-large-db.sh <out.db> [count]` builds a synthetic DB (default 200 000
  photos, no files); point a server at it with `DATABASE_URL` on a spare port.
  Browser perf: `PERF=1 PERF_BASE_URL=http://localhost:<p> npm run test:perf` against a release server on that
  data; skipped otherwise. Setup: seed, give alice a password (create a throwaway user with `-p perf`, copy its
  `password_hash` to alice; `PERF_PASSWORD` defaults to `perf`), `npm run prod`, start the release server with
  `SCAN_NEW_FILES=false`. Last run (200k photos, Chromium): first tiles ~0.7 s, ≤ 2000 tiles in the DOM, bounded
  heap, long tasks up to ~340 ms (headless software raster, not grid JS).
- `npm run typecheck` (tsc over JSDoc-typed `assets/js` and the specs) and `npm run knip` (unused
  files/exports; add new page scripts to `entry` in `knip.jsonc`) must pass.
- The owner keeps a dev server running on port 8080 against `test.db` and runs `npm run dev`: never
  touch that port or that database, and don't edit `assets/css/main.css` by hand.
